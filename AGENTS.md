# Project Instructions

The single source of truth for agent rules in this repository. `CLAUDE.md` only imports this file; never copy these rules into another file.

## Context loading

- Do not read `implementation-plan.md`, `docs/plan-v*.md`, `first-draft.md`, `docs/plan/`, `docs/mechanics.md`, the plan archives or `README.md` unless the user asks, `/implement-phase` or `/brainstorm` runs, or the task changes gameplay rules. Even then, grep for the relevant heading and read that section, not the whole file.
- If a request conflicts with a recorded decision in the plan, ask rather than silently choosing.
- Do not re-read a file already in context this session.
- For code under `app/src`, query the codegraph index first when it is available (`codegraph_explore`, or the `codegraph` CLI): one call returns a symbol's source, its call paths and what depends on it, and the source it returns counts as already read. Use `grep` or a line-range read only for a single known line, or when the index is unavailable. Do not call it before an edit merely to survey blast radius.
- codegraph does not index Markdown, JSON or configuration. For those, grep for the relevant heading or key and read that range, never the whole file.

## Tool use and replies

- Create and change repository files with the Write and Edit tools, never with `cat >` heredocs, `sed -i` or other shell rewrites: those bypass file tracking and echo whole files back into context. Throwaway scripts outside the repository, for example under `/tmp`, may still be written with a heredoc.
- One exception: a purely mechanical rename or replacement across more than five files (an identifier, an import path) may run as one reviewed command, for example `git grep -lz '\bOldName\b' -- app/src | xargs -0 perl -pi -e 's/\bOldName\b/NewName/g'`. Print only the list of changed files, run `npx tsc -b` afterwards, and name the command in the report. Anything that needs judgement per file still goes through Edit.
- Files generated by the project's own code (an export the tagger produces, a frozen copy of a file from git) may be written by the script or `git show` that produces them, never retyped through Write.

## Context budget

Every turn resends the whole conversation, so context size, not output, drives cost. A session past about 300k tokens of context costs several times more per turn than a fresh one.

- Read a file by the section you need (`offset`/`limit`, or a grep for the heading or symbol), not whole. Prefer one narrow `codegraph_explore` query with exact symbol names over a broad question.
- Cap command output: pipe compiler errors through `| head -40` or `| cut -c1-200`, and filter test runs to their failures and summary (`| grep -E "FAIL|×|Tests "`). Read a full log file only for the failure you are fixing.
- Do not rerun the full test suite while iterating; run the focused files, then the whole suite once at the end.
- Delegate bulk mechanical work - fixing dozens of test fixtures after a data or type change, a rename across many files, a survey of many call sites - to a subagent with a precise brief, and keep only its summary in the main session.
- Implement one plan phase per session. For a request covering several phases, follow the orchestration rule in `.claude/skills/implement-phase/SKILL.md`, or stop after each phase and ask the user to `/clear` before the next.
- Default to terse chat replies: answer first, drop preamble and restatement, keep every technical fact. Anything persisted stays in full prose - commit messages, plan and phase files, code comments and deferred-register entries - as do questions, warnings and confirmations.

## Scope and design

- Implement only what was requested. Preserve unrelated work, stop for unapproved design choices, and never start a later plan step automatically.
- An orchestrated `/implement-phase` run (several phases, a plan or a plan document) is the one exception: it runs every unit of the plan and never asks the user. In such a run, "ask" and "stop for a user decision" in this file mean: do not act on the open point, mark the unit `blocked` with the decision it needs, continue with the units that do not depend on it, and report it at the end. Questions belong in `/brainstorm`, before the plan is written.
- Follow YAGNI, DRY, TDD and SOLID without speculative frameworks. For testable behaviour, write a focused failing test first, then make the smallest change that passes it.
- Ask before changing gameplay scope, rules or tuning. Record approved deviations and comparison-breaking rules versions.
- Gameplay values use named constants and typed configuration with units and a documented source or user approval. Never invent ROTMG fidelity claims.
- [The deferred register](docs/deferred-work.md) lists recognised, postponed, **unapproved** work. Do not implement anything listed there without an explicit user decision promoting it.
- Out of scope: a backend, accounts, player attacks, seal activation, touch controls, shrinking arenas and a tuning UI. A tagger control that edits only a study's typed estimates and never game data is not a tuning UI (plan V16 S47). A tagger editor that produces monster JSON for a person to apply, and that the running game never reads, is not a tuning UI (plan V18 L01).
- `WebFetch` returns an empty document for RealmEye wiki pages. Fetch them with `curl` and a desktop user agent, then strip script/style tags and parse the rendered markup.

## Architecture

- Pure frontend in `app/`: React, TypeScript, Vite, Phaser, CSS Modules, npm, Vitest and Playwright. Install packages through npm and preserve the lockfile.
- Models, configuration and simulation stay independent of React, Phaser, DOM and localStorage. Phaser owns runtime integration and drawing; React owns screens and HUD; a storage adapter owns persistence. Never update React per projectile per frame or add a second simulation clock.
- A bullet's motion kind is authored per projectile: `linear`, `boomerang`, `turning` or `wavy`. Reversing velocity once and expiring only by lifetime describes `boomerang` only. A bomb is a separate shot type (`"type": "bomb"`) with its own runtime list: it expires by its travel time and hits only by detonating. The per-projectile once-only hit rule applies to every kind and type. No stored firing origin, collision despawn or global invulnerability unless explicitly approved.

## Verification

Checks cost time and tokens, so run them at the end of a unit of work, not after each edit.

- While iterating, run only the focused test file from `app/`: `npx vitest run <path>`. Before reporting a test change also run `npx tsc -b`: Vitest strips types, so a bad fixture passes there and fails the build.
- Delegate verification runs (`npm run verify`, targeted Playwright) to the `verifier` subagent (Haiku, `.claude/agents/verifier.md`). It may apply only `oxlint --fix` and single-file typecheck fixes and reports everything else. Draft commit messages, when asked to commit, with the `commit-drafter` subagent and review the draft before committing.
- A run of several phases or of a whole plan is accepted by the `critic` subagent (Opus, read-only, `.claude/agents/critic.md`), not by the session or subagent that wrote the change. Give it the plan and the base ref and never the implementer's report; it runs after the `verifier`, at most twice more after fixes.
- Name the repository root in every subagent brief, from `git rev-parse --show-toplevel`. The devcontainer mounts the repository under the name of its host folder, so no instruction file may contain an absolute path.
- Run `npm run verify` from `app/` once when a plan phase or a set of code edits under `app/` is finished, before reporting. It runs `lint`, `typecheck`, `test` and `build`, prints one line per gate, and puts full logs in `app/test-results/verification/<gate>.log`. Read a log only when the printed excerpt is not enough. Do not run the four gates separately.
- Skip `npm run verify` when only documentation, plans or agent instruction files changed.
- Playwright is not routine while iterating; CI runs the full suite on every push.
- Before a branch is pushed for a pull request, and once at the end of an orchestrated `/implement-phase` run, delegate the full non-soak browser suite to the `verifier`: `CI=true npm run test:e2e -- --grep-invert @soak` (about 10 minutes). `npm run verify` runs no browser test, so a spec still asserting behaviour a change deliberately altered otherwise first fails in CI (PR #12: a moved player spawn, a removed control, a bumped draft version). Fix a failing spec to the recorded behaviour; never loosen it to pass.
- A browser spec reads a version or other value the app defines from its source, never a copied literal: import it as `tests/app.spec.ts` imports `encounter.json`, or read the export through the dev server with its `sourceExport` helper when Node cannot load the module. `sourceExport` does not work in a test the production preview also runs.
- The three 60-second `@soak` tests (real-time frame timing and runtime bounds) run locally only with `PLAYWRIGHT_SOAK=1`, or when `CI` is set. CI always runs them and keeps their frame-timing JSON in the `browser-results-*-soak-*` artifact. Set `PLAYWRIGHT_SOAK=1` for any step that measures or compares frame timing, because CI-runner timings are not comparable with the recorded local baseline. When adding or changing a Playwright test, run only that test: `npm run test:e2e -- --grep "<pattern>"`. Run the full suite only to reproduce a CI failure or when the user asks for an acceptance run.
- A property, contract or mutation test that fails on current code is a finding: record its seed, path and counterexample, keep the test as `test.fails` with a comment citing the record, and stop for a user decision (plan V22 A10). Never weaken it or change simulation behaviour to make it pass.
- `app/src/game/config/rules-fingerprint.json` must change in the same change as any gameplay data edit and its `rulesVersion` bump (plan V22 A12); the fingerprint test says which of the two is missing.
- Before reporting a change to a module in the Stryker mutate globs (`app/stryker.config.mjs`), delegate `npm run test:mutation:diff` to the `verifier` subagent; never run a mutation command in the main session. When the change touches more mutated modules than the diff limit (4), cover all of them in consecutive batches of at most four named files, `npm run test:mutation:diff -- src/a.ts src/b.ts`, and never choose a subset: the author of a change does not pick which of its modules are checked. Never call `npx stryker run` directly: its HTML and console report merge the incremental cache, so it lists every module and looks like a full run. Stryker rewrites sources in place while it runs, so make no edits under `app/` until the verifier reports.
- Never run the full mutation suite (`npm run test:mutation`, about 3 hours) from an agent session, the verifier included. Give the user the command to run in their own terminal, or leave it to the scheduled `mutation.yml` run.
- Run `npm run bench` against `main` and the benchmark gate before reporting a change to the simulation's hot path: `simulation.ts`, `projectiles.ts`, `bombs.ts` or `geometry.ts`.
- [The quality-gates reference](docs/quality-gates.md) describes every gate, its command and how to reproduce a failure.
- Report the checks you actually ran and any blockers. Never claim a check passed when it did not run.

## Git and deployment

- Never commit, push or claim a live deployment without authorization and evidence. An orchestrated `/implement-phase` run is authorized to commit locally on its work branch, as its skill describes, and to nothing more.
- After pushing, do not watch or poll GitHub Actions or the Pages deployment. Report the push and stop.
