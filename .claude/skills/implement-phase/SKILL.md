Act as a Senior Software developer, follow TDD, SOLID, YAGNI and DRY principles. Focus on reusing existing over creating new solutions.

Implement only what the user named with this command: `$ARGUMENTS`. If that reads as a literal placeholder, use the ID the user typed after `/implement-phase`. If it is absent or invalid, ask for it. The ID is either a whole phase (`23`) or a single step of one (`23.6`); a step ID means implement that step alone, then stop. Follow [the project instructions](../../../AGENTS.md).

**Several phases, a whole plan or a standalone plan document** (for example `plan-v23`, `97-100`, `docs/trust-plan-2026-11-19.md`, or an explicit request to run more than one phase): do not implement them in this session, because the context of every finished phase would be resent on every later turn. Act as an orchestrator instead. A unit below is one phase, or one item of a standalone plan document. Your context holds the plan's order, the subagents' reports and nothing else.

**Autonomy.** The plan is the user's last word: every question was settled when it was written. From the start of the run to its final report you never ask the user anything and never wait for an answer. Where this skill or AGENTS.md says "ask" or "stop for a user decision", an orchestrated run does one of these instead:

- **A choice the plan leaves open** (a name, a file layout, which of two equivalent approaches): take the smaller option that AGENTS.md allows, write it under "Decisions taken", and continue.
- **A failure** (a failed gate, a `FAIL` from the critic, a subagent that returns nothing usable): repair it as described under "Repair".
- **A decision that is the user's alone**: a gameplay rule, value or scope the plan does not give, a deferred-register item, an A10 finding, or a conflict between the plan and a recorded decision. Do not decide it and do not work around it. Leave the tree as the rule requires (an A10 finding stays as `test.fails` with its record), mark the unit `blocked` with the one decision it needs, skip the units that depend on it, and continue with the rest.
- **An action the permission system refuses, or that the plan marks for the user** (a push, a repository setting, a workflow dispatch): do not retry it or reach it another way. List it under "Needs you" with the exact command.

A Bash call refused only because a hook changed its input is not a refusal: issue the quoted input once more, unchanged, and say so in every brief.

**Git.** An orchestrated run may commit locally and do nothing else to history. Work on the branch the plan names; when it names none and the current branch is `main`, create a branch named after the plan. Commit each unit once its verification passes, with a message from the `commit-drafter`. Never push, open or comment on a pull request, merge, amend or force anything, unless the command that started the run says so.

**Steps.**

1. **Orient.** Read only the plan's Phase Index, or the document's order section, and the dependency order. Find the repository root with `git rev-parse --show-toplevel` and state it as an absolute path in every brief; no agent file may assume one. Note the starting commit: it is the base ref for the review.
2. **Implement one unit at a time.** For each unit in order, launch one `general-purpose` subagent with `model: sonnet` and this brief: "In <repository root>, implement <unit> by following steps 1-5 of `.claude/skills/implement-phase/SKILL.md` (this skill cannot be invoked as a command from a subagent, so read and follow it) and AGENTS.md. Do not ask questions: where the unit leaves a choice open, take the smaller option and report it. Run only the focused test files and `npx tsc -b`. Do not run `npm run verify` or any mutation command. Do not start a subagent, commit, or mark anything complete. Write the execution record of step 7 without changing a status. Report in under 200 words: changed files, tests added and whether each was seen failing first, choices made, findings." For an item of a standalone plan document, name the document and the item's heading in place of the phase, and tell the subagent to read that section and the document's decisions table instead of steps 1 and 2. Never run two implementing subagents at once: they share one working tree, the heavy simulation tests time out under load, and Stryker rewrites sources in place.
3. **Verify each unit yourself.** A subagent cannot start another subagent, so the implementing subagent cannot reach the `verifier`. After each report, run `npm run verify` through the `verifier`. On a pass, commit the unit. On a failure, repair.
4. **Mutation, once.** After the last unit, run `npm run test:mutation:diff` through the `verifier` over every changed module in the Stryker mutate globs. When there are more than four, name them in consecutive batches of at most four until all are covered; never choose a subset. Send the undetected mutants on changed lines to one implementing subagent to add the missing tests, verify, and commit. List the mutants that remain in the report; do not chase them further.
5. **Review.** Launch the `critic` subagent (`.claude/agents/critic.md`) with only the repository root, the paths of the plan and phase files, and the base ref. Never give it an implementing subagent's report or your own summary: a report is a claim, and the critic collects its own evidence.
6. **Fix, at most twice.** Send each `FAIL`, in the critic's words only, to a new implementing subagent, then run the `verifier`, commit, and launch a new `critic`. After two rounds, stop fixing and report what still fails.
7. **Record and report.** Mark a unit `complete`, and archive its phase file as step 7 describes, only when the critic returned `PASS` for every one of its acceptance criteria. Then write the final report.

**Repair.** Give a new implementing subagent the unit and only the decisive lines of the failure with its log path, then run the `verifier` again. Allow two repair rounds for a unit. If it still fails, set its changes aside with `git stash push -u -m "blocked: <unit>"` so that the next unit starts from a passing tree, mark it `blocked` with the failing check, skip the units that depend on it, and continue. Launch a subagent that returns nothing usable once more; if that fails too, end the run with the final report. Never reach a pass by editing an acceptance criterion, raising a timeout, lowering a threshold, loosening or deleting an assertion, or skipping a gate.

**Final report.** One table for the whole run: criterion, verdict, evidence, and who verified it. Then "Decisions taken"; the checks that ran with their results, and those that did not run; "Blocked", each unit with its failing check or the decision it needs and the name of its stash; "Needs you", each action with its exact command; and the branches and commits. Return when every unit is `complete` or `blocked`. Never return earlier to ask something, and never report a unit as complete because the run is ending.

If subagents are unavailable (rate limit, no Agent tool), implement the first phase only in this session, record it, and end with a report that says each remaining phase needs a session of its own.

1. **Load the owning plan once per session, by section.** More than one `docs/plan-v*.md` can exist; find the one whose Phase Index lists the requested phase, or the phase part of a step ID (grep `^| <phase> |` across `docs/plan-v*.md` if `implementation-plan.md`'s Current Plan table does not make it obvious). Read that file from the top through its Phase Index section. Skip "Recorded User Decisions" and "Target Data Shapes" unless the step cites a decision (its lettered ID) or a data shape; then read only that part. Do not reread these sections for a later step in the same session.
2. **Read only what the ID names.** The Phase Index line links the phase file under `docs/plan/`, named `phase-*.md` containing the phase number. For a step ID, read that step's `### Step <id>` section only, plus one grep of the file's `### Step` and `Status:` lines for the phase's step list and statuses; do not read the whole phase file. For a whole-phase ID, read the phase file. Completed dependencies are summarised by their one-line index entries; open an archive in `docs/plan-archive/` only when a summary does not answer a specific question.
3. **Check dependencies.** Use the status lines from step 2. If any dependency is not complete, report the blocker and stop. Do not implement dependencies.
4. **Read cited sources by section.** The step and the active plan file's Sources section name the documents an authored value must trace to (mechanics contracts, source extracts). These are large: grep for the decision IDs, mechanic names or table rows the step cites and read those sections only. If required sourcing or approval is missing, ask and stop dependent work.
5. **Implement with TDD.** State the scope and the focused checks. Write a focused failing test first for testable behaviour, then the smallest change that passes it. While iterating, run only the focused test files.
6. **Verify once.** When the phase is done, run the phase's focused checks, then delegate `npm run verify` (once) and only the Playwright tests the phase names to the `verifier` subagent (Haiku) and use its report. Do not broaden scope to unrelated failures or claim unavailable checks passed.
7. **Record.** Write the execution record below the phase's prompt in its phase file. Mark the phase `complete` in the phase file and on its plan index line only if every acceptance criterion is met. If this completes the phase, move the phase file to `docs/plan-archive/phase-<n>.md` and give each index line a one-sentence outcome.
8. **Report** changed files, check results, open questions and blockers, and manual verification steps. Do not start the next phase, commit or push.
